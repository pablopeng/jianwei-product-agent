# 精简两阶段与聊天交互

## 这次改动解决什么

此前回复中的“两次校验失败”是程序的数据格式、来源格式校验拦截，不等同于真实商品没有可用信息。原来把原文逐字引用、来源类型、SKU图谱和版本信息都放进模型业务输出，增加了结构化错误，也导致程序问题变成商家的补资料任务。

现在将业务内容与后台记录分开。来源、版本仍保留，但不要求商家理解或填写这些字段。摘要允许归纳表述；宣传与买家感受自动归到相应类别，不因归类错误阻断整个商品。

## 第一阶段：五块商品档案

```json
{
  "product_info": {
    "name": "商品名称",
    "category": "品类",
    "ingredients": ["明确的通用配料"],
    "attributes": ["储存、保质期、产地等明确属性"]
  },
  "specifications": [
    {"name": "规格或口味名称", "details": ["仅适用于本规格的信息"]}
  ],
  "original_selling_points": ["商家原有描述"],
  "buyer_feedback": ["买家反馈摘要"],
  "cautions": ["冲突、缺失或待确认的信息"]
}
```

材料较多时分批读取、汇总去重、复核规格范围，不通过截断原文压入一次请求。模型读到的全部文本片段与图片都有来源。不同口味配方不完整时，不把单一款式配料列为全商品通用配料；已明确对应的配方仍保留在规格信息中。

目标是完整收集资料中能支持的信息，不是证明原始资料真实。无法确认或冲突信息单列，不擅自选择一个值。多SKU、单件与套装、不同生产基地不因口径不同就自动算冲突。

## 第二阶段：卖点与优先级

```json
{
  "selling_points": [
    {"text": "一条有依据的卖点", "priority": 1},
    {"text": "另一条有区分度的卖点", "priority": 2}
  ]
}
```

数量不预设3—5条。信息充分时可以多写，去重后按购买决策价值排序，1最高。后台保存每条卖点使用的档案信息，导出业务结果时不夹带后台记录。主标题、详情长文和重塑详情页不属于本期输出。

原始材料有疑问，只限制受影响的卖点。认证资料不足时不承诺认证，仍可用规格、储存和使用方式等已知信息生成。格式错误由程序修复，不要求商家为格式问题补认证或实物标签。

## 工作台与聊天

- Schema默认显示上述简洁结构示例，高级JSON Schema按需打开。
- 聊天支持收藏、置顶、归档和恢复，状态持久化保存。
- 用户消息和回复可单条复制，最新回复可以重新生成。
- 重新生成复用原问题，不重复插入用户消息；上一版保留，失败时恢复上一版。
- 旧对话和旧输出继续可读；新生成使用精简合同，旧格式仅用于历史兼容。

## 实测与边界

54项程序/HTTP测试通过。浏览器验证了简洁Schema预览、复制、重新生成、收藏与置顶。之前失败的真实水饺样例使用已配置DeepSeek完成了分批整理、合并、一致性复核和卖点生成，最终一次实测约38秒返回14条带优先级卖点。

实测证明链路可以完成，不代表每一条文案已经通过人工业务评测；模型摘要与语义支持仍需抽查。二期的卖点配图、图文重组和详情页重塑尚未实现。
