# 商品卖点 Agent 第一版设计

## 产品目标

商家提供已有商品属性、规格、详情图文、宣传文案及买家评价，Agent整理证据、识别冲突，按食品饮料类目策略生成可用于货架的卖点。已有详情页有卖点也可以作为输入，价值包括信息汇集、去重、排序、解释购买理由和适配展示长度。不能承诺每个商品都需要新增卖点，也不能据此声称转化已经提升。

首期使用清理后14条真实食品饮料商品。保留食品饮料行业范围，按零食糕点、粮食干货、冷冻食品、水产、饮品茶叶选择不同表达策略。样本适合做首轮验证，不代表全行业分布。

## 三份数据合同

### 原始输入：input.schema.json

`product_id`及`materials`由接入层创建。每个material拥有稳定ID、kind、label、locator、text、origin及图片引用。字段完整但允许未知值用空字符串，不能把未知数值写成0。

`kind`描述载体/信息来源：商品属性、规格、商详文字、图片、宣传文案、买家评价、旧AI派生内容、商家补充。

`origin`描述信息出自谁：merchant / platform / buyer / ai / unknown。不能因为原表字段叫“商品基础属性卖点”就把内容自动认定为客观属性。

图片是材料载体，读图后得到的信息再分配到下面五类；不另建一个与属性平行的“图片事实”区。一个图片可支撑多个类别的信息。第一版14条快照中有图片引用，尚未全部下载，不假装已完成图片理解。

### 第一阶段输出：product-knowledge.schema.json

| sections字段 | 含义 | 例子 |
| --- | --- | --- |
| product_attributes | 商品身份、配料、储存、包装等属性 | 花生添加量≥5% |
| specifications | 与SKU、数量、重量、组合相关的信息 | 278g×2袋，仅该SKU适用 |
| detail_content | 详情页中的使用、加工、可见设计等信息 | 独立小包装、切丝形态 |
| marketing_claims | 商家已有的宣传主张 | 商品页描述“香甜不腻” |
| buyer_reviews | 消费者个人体验 | 某条评价提到“酥脆” |

五类每条都使用相同的observation结构：

| 字段 | 用途 |
| --- | --- |
| id | 后续卖点引用的稳定信息ID |
| name / value / unit | 保留原意、数字、单位和限定条件 |
| evidence_kind | explicit_attribute / visual_observation / merchant_claim / buyer_experience / ai_derived |
| status | supported / unverified / conflicted；supported表示来源支撑，不代表第三方事实核实 |
| scope | product通用 / sku指定 / unknown不明确；sku_ids列出适用规格 |
| evidence | source_id、原文quote、定位locator、text或image_read读取方式 |

顶层另有`skus`、`category`、`issues`和`questions`。SKU ID由第一阶段建立并跨轮保留。问题记录影响范围及解决状态；只影响克重的冲突可以通过省略克重继续，不阻塞其他有依据的卖点。新材料不会自动覆盖旧材料，而是触发重新整理及冲突消解。

`material_revision`由原始输入内容计算，避免新增图片或商家补充后继续使用旧档案。

### 第二阶段输出：selling-points.schema.json

| 字段 | 用途 |
| --- | --- |
| target | 目标SKU或通用卖点、受众、场景、展示位置、语气 |
| headline | 一句主卖点，初版≤36字 |
| points | 最多5条，title≤24字、body≤100字；包含dimension、claims、sku_ids |
| claims | 文案中的可追溯断言，关联第一阶段observation_ids |
| detail_copy | ≤500字的详情说明 |
| headline_claim_ids / detail_claim_ids | 防止标题和长文案游离于证据体系 |
| omissions | 主动避开的冲突或无依据内容 |
| questions | 本次必要的补充问题 |
| change_summary | 面向商家的修改摘要 |
| material_revision / knowledge_revision | 资料及档案内容版本，防止结果过期 |

长度是首版产品默认，不是平台规定。claims区分客观商品事实、商家描述、买家反馈、使用建议。例如“独立包装”是事实，“可放办公室分次取用”是基于该事实的使用建议。

输出为draft；无可支撑内容时为needs_input，留空文案并提问。结构校验不等于文案质量或事实真实性通过评测。

## Agent与两个阶段的关系

两个阶段是可调用能力，主Agent以工具循环选择下一步。不存在每次用户发言都必须“整理→生成”的路由。

| 用户意图 | 合理的处理路径 |
| --- | --- |
| 帮这个商品生成卖点 | 查状态→必要时整理→调用Skill生成 |
| 先看配料有哪些 | 检索/读取材料→直接解释，不生成卖点 |
| 为什么出现278g和300g | 搜索不同来源→核对/整理→解释冲突，必要时追问 |
| 只改短第二条 | 读取已有结果→定点改写，其他卖点保持不变 |
| 我确认当前包装是278g | 登记本轮原话→资料版本更新→按需重新整理，不把旧结果当新结果 |
| 突出低糖一点 | 先查有无证据；这是表达诉求，不能登记为低糖事实 |
| 材料不足 | 可以避开缺失字段时先生成有限结果；必要缺失则暂停等待回复 |

当前检索工具查找的是商家已提供材料，支持多次搜索和分页。公网商品链接抓取是后续连接器能力，尚未实现，工具不会假报联网成功。未来新增连接器时，抓回内容也应先登记为materials，再走同一证据合同。

工具失败返回可读错误供Agent调整。结构化模型调用最多修复一次，主循环每轮默认最多10批工具决策，防止无穷调用。会话保存原始材料、知识档案、已有卖点、对话与工具事件，不存储API密钥或隐式思维链。

## 已实现的验证与仍需验证的部分

代码校验来源存在、文字引用属于原文、图片是否实际提供给模型、ID唯一、AI/评价不能升级为商品属性、SKU适用范围、冲突使用、版本过期、标题/详情引用、定点改写不影响其他卖点。

这些规则不能判断所有语义问题：例如标题是否偷偷增加断言、图片文字是否识别准确、成分比例是否真的支持某个消费者利益，都需要模型质量评测与人工抽查。当前测试使用ScriptedClient验证程序行为，不冒充DeepSeek实跑结果。

## 麻花示例

真实输入有配料、已有卖点、评论及长图。结构化净含量278克与详情底部300克存在冲突。人工设计示例保留花生≥5%、蜂蜜≥0.7%、独立小包装，省略克重，生成两条短卖点，并把每条断言关联到原始信息。原页面已有分享场景，本示例不会把它包装成Agent新发现。

这个示例用来展示合同和引用关系；尚未用API生成，不计为正式模型案例交付。
